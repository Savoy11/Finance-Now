### 1. The CI Success Gate never checks `security-scan` or `terraform-validate` · `P1`

**Evidence:** `.github/workflows/ci.yml`, `ci-success` job. `needs:` lists six jobs:

```yaml
    needs:
      - backend-lint
      - backend-test
      - frontend-check
      - docker-build
      - security-scan
      - terraform-validate
```

The step that decides the result checks four:

```bash
          check backend-lint   "${{ needs.backend-lint.result }}"
          check backend-test   "${{ needs.backend-test.result }}"
          check frontend-check "${{ needs.frontend-check.result }}"
          check docker-build   "${{ needs.docker-build.result }}"
          [[ $status -eq 0 ]] || exit 1
```

The same file names this exact trap, in the `frontend-check` job's own comment:

> "The ci-success gate is `if: always()` and checks each job's result by name, so a new job that
> is added to `needs:` but missed in the check block — or vice versa — passes silently."

Two commits on this branch walked past it. `c7ae0a3` removed `|| true` from the Node audit —
`git diff origin/main...HEAD -- .github/workflows/ci.yml` shows
`-          npm audit --audit-level=high || true` / `+          npm audit --audit-level=high`,
annotated *"GATING since 2026-09-08 … A check that cannot fail is not a check."* And `f4c850f`,
whose entire purpose was the success gate ("CI: stop the success gate reporting a cancelled run as
a failure"), rewrote the check block into a `check()` helper and still listed only four jobs.

Blast radius beyond npm audit: the same `security-scan` job runs Trivy at `CRITICAL,HIGH`, and
`terraform-validate` runs `terraform fmt -check -recursive` and `terraform validate` — while this
branch changes `infrastructure/terraform/eks.tf` (+86), `iam.tf` (+13) and `main.tf` (`264d218`,
EKS module v19.21→v20.37). `docs/CI-REMEDIATION.md` lists both jobs in its "Job status" table as
things that are meant to be green.

**What is wrong:** The check named "CI Success Gate" reports success while two of its six
dependencies have failed.

**Why it matters:** That is the check a branch-protection rule and a reviewer read. A HIGH npm
advisory, a Trivy CRITICAL, an unformatted or invalid Terraform change — each ships green. The
2026-09-08 decision to arm the audit gate has not actually taken effect.

**Suggested fix:** Add `check security-scan` and `check terraform-validate` to the block — or, if
either is deliberately advisory, remove it from `needs:` so the workflow stops implying it gates.

*Importance:* High — it is the release gate, and it silently un-armed a security control landed in
this same batch. · *Efficiency:* High — two lines. · *Practicality:* High — the `check()` helper is
already there.

  provider keys, each set live in the loop at line 477.

  plus `DEFAULT_LIVE_APR_KEY` (line 238) covering 15 non-ETH coins for wallet-category rows.

28 to 51 providers **without adding live rate sources** … Improving this ratio is the open work, not

honest either way (`aprDisplay()` badges live only when `sources[key] === 'live'`, and refuses to

to whatever gets built next.

**Suggested fix:** Re-run `npm run audit` on the owner's machine and set both rows from what it
says. If the rung works, the "without adding live rate sources" sentence and the "open work" framing

*Importance:* Medium-high — a capability claim about numbers users act on, wrong in an
