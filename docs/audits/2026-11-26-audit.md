## Findings

### 1. The index-fund replay annualizes paths under a year, beside a tile that deliberately does not · `P1`
**Evidence:** `frontend/src/lib/data/trackedPortfolioViews.ts:183` — `YEARLY_AFTER_DAYS = 365`, commented
*"The yearly figure shows once the first money put in is this many days old (owner, D208)"*; `:313-314` — under
that age `portfolioReturn` returns `kind: 'total'` and the tile renders "Total return so far".
`frontend/src/lib/data/benchmarkCompare.ts:132-136` — `replayAgainstBenchmark` runs `moneyWeightedRate`
unconditionally, with no age gate; `frontend/src/components/portfolio/tracked/BenchmarkCompareCard.tsx:118-121`
— the card prefers it: `replay.ratePct != null ? '${symbol} path, per year' … '{formatReturnPct(replay.ratePct)} a year'`.
Worked through the module's own solver this run: a +2.5% gain over 90 days renders as **"+10.5% a year"**.
`benchmarkCompare.test.ts`'s only rate test is the 2-year case (`:50`); no test touches a path under a year.
**What is wrong:** for a portfolio whose first money is under `YEARLY_AFTER_DAYS` old — every newly tracked
portfolio — the side-by-side shows the portfolio as a plain total and the benchmark as an annualized rate, on
the same dates, with nothing saying the units differ (`benchmarkMethodNote` describes the replay, not the unit).
**Why it matters:** the card exists to answer "how did I actually do against the index". A portfolio up +2.5%
in 90 days beside "VOO path, per year +10.5% a year" reads as the index doing 4× better **when the two paths
performed identically** — the short-horizon annualization distortion D208 removed from the portfolio's own
figure, reintroduced on the other half of the comparison.
**Suggested fix:** show `replay.totalPct` (already computed) whenever the portfolio's own figure is a total —
the card already receives `earned`, so `earned.kind === 'total'` is the gate — and pin the symmetry with a test.
*Importance:* high — a misleading comparison on a figure users act on, in the common case · *Efficiency:* high —
both figures and the gate are already in hand · *Practicality:* high — a few lines plus one test.

### 2. The Brief's grounded earnings dates skip tracked-portfolio stocks; CLAUDE.md says "held/watched" · `P2`
**Evidence:** `frontend/src/app/(dashboard)/brief/page.tsx:98-111` — `equitySymbols` is built from watchlists
and what-if portfolios only; `tracked.data` (the tracked holdings, fetched at `:88` and already awaited before
Generate at `:176`) is never added, though `trackedBriefSymbols` labels each with its class
(`trackedPortfolioViews.ts:46-50`). The page's own comment (`:92-93`) says *"earnings only with Equities on and
stocks held or watched"*, and CLAUDE.md's Daily Brief row (updated in this window) says *"the held/watched
stocks' expected reports go into the prompt"*. T-453's vocabulary makes tracked holdings the "held" stocks:
*"the Daily Brief adds the tickers held in tracked portfolios"*.
**What is wrong:** a user whose stocks live only in a tracked portfolio — their real holdings — gets a Brief
that discusses those tickers (they are in the universe via `collectContext`) but whose "Worth watching" context
carries no earnings dates for them, so the agent falls back to web search for exactly the dates T-475 exists to
ground; and the documented claim ("held") is wider than the code.
**Why it matters:** the feature's stated point (D245) is that the agent quotes dates the app knows instead of
what search finds; the gap lands on the user's real positions first. Mild harm, but it is both a coverage gap
and documentation drift in the same sentence.
**Suggested fix:** feed the tracked equity symbols into `equitySymbols` (the class label is already in
`trackedBriefSymbols`' output, or add a sibling helper that returns them raw), or narrow the CLAUDE.md/page
wording to "watched and what-if-held".
*Importance:* low-medium · *Efficiency:* high — the data is already fetched on the same page · *Practicality:* high.

### 3. Security-activity timestamps omit the year · `P3`
**Evidence:** `frontend/src/components/settings/SecurityActivityPanel.tsx:18-19` —
`when()` formats `{ month: 'short', day: 'numeric', hour: 'numeric', minute: '2-digit' }`, no year; the route
serves the newest 50 rows with no time bound (`security-activity/route.ts:68`).
**What is wrong:** on a quiet account, 50 rows can span years; a "Sign-in failed" from November 2026 and one
from November 2027 both render "Nov 25, 3:41 PM".
**Why it matters:** this is the surface built for noticing a sign-in attempt you did not make (T-474's own
stated purpose); an old refused sign-in reading as recent sends an account holder chasing a breach that
happened a year ago — or dismissing a recent one as the old one they remember.
**Suggested fix:** include the year (always, or when the row's year is not the current one).
*Importance:* low · *Efficiency:* high · *Practicality:* high — one format option.
