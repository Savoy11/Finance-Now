| D234 | T-083 (the P3 review's D1): the rollout posture on module entitlements. `useEntitlementStore` was localStorage-only — fine for a personal tool, trivially editable the moment modules are paid SKUs — while the `entitlements` table sat in the schema with no route serving it (auth.md Goal B step 4, "the one with real security weight"). The owner took the cluster's next piece and was asked what a brand-new account gets at launch: standard modules on with Builder per-grant, everything on, or core only | **Owner:** *"Standard on, Builder granted (Recommended)"* | Built: (1) **The posture.** Crypto, Equities, Macro Markets and ETFs & Funds are ON for every account and stay personal on/off toggles, now synced to the account's rows; **Portfolio Builder is a premium module** (the registry's new `premium` flag) that a real account holds only with a grant row — `npm run entitlements -- --grant builder --user <email>` until billing writes the same rows (T-084). A grant past its `expiresAt` reads as not granted, so billing's terms already work. (2) **The enforcement with the weight**: a session's own toggle can never reach a premium module (`canUserToggle`, refused 400 by the route), so no account self-grants Builder; the Settings panel shows "Included / Not included" instead of a toggle and `ModuleGate` says the module "isn't included with this account" rather than offering a dead re-enable link. (3) **Dark until launch, local mode unchanged**: the shared local user keeps today's behaviour exactly — everything on by default and togglable, Builder included, as the schema's own comment promised ("in local dev is granted") — and real accounts only exist after the launch flip. (4) **No new migration** (the table is in 0000), rows upserted never deleted, the store keeps its `isEnabled`/`setEnabled` interface and `skipHydration` contract with a one-time import of the browser's old toggles (never a saved "builder off" over grant rows), and **no database means today's browser-only behaviour**, quietly. Rules pure in `lib/modules/entitlements.ts`, tested with the route/store/gate wiring in `entitlements.test.ts`. In the ledger: T-083 closes; T-084 (billing writes the rows) stays parked. Module data routes are not per-module gated server-side — the UI and tools are the gate; hardening that is billing-time work, noted here so it is a choice and not an oversight. |
| D235 | T-088's last piece, audit logging, taken up on the owner's word (*"then lets do the audit logging"*) once D234 landed. T-185 had specified the shape since the production-readiness scorecard: an `audit_log` table whose rows the database itself refuses to change — a Drizzle custom migration with a BEFORE UPDATE OR DELETE trigger raising an exception (WORM, tamper-evident) | **Owner:** *"Merge when green; then lets do the audit logging"* | Built: (1) **Migration 0013** creates `audit_log` and the WORM trigger, exactly T-185's prescription; rows can only ever be inserted. (2) **What is logged**: account created; sign-in succeeded and each refusal (wrong password, forced reset, wrong/throttled two-factor code) — only for an email that matched an account, so the log never records strangers' typos or probes which accounts exist; password resets and owner-issued reset links; two-factor on/off, recovery-code use and regeneration; module toggles, grants and revocations; data exports. The four owner commands log as `owner-command`. (3) **The lines drawn**: portfolio and watchlist edits are deliberately not logged (the trade ledger is already its own append-only record; activity noise would bury the sign-ins this log answers for), and **no IP address or browser string is kept** — that would be new personal data the draft Privacy Policy does not name; adding it is a counsel-review question, flagged here. (4) **Recording never breaks the action**: the writer swallows every failure after saying so, and a database without 0013 reads as "not logging yet", never an outage — the 0008 pattern. (5) **The record survives the account**: `user_id` carries no foreign key (a cascade delete would be refused by the trigger anyway), and because the column is still named `user_id`, "Download my data" includes an account's own audit rows automatically. With D173 (rate limit), D233 (2FA) and this, **T-088 closes — the whole Phase 6 hardening row is built** — and T-185 closes with it. |
